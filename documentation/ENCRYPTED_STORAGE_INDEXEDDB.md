# Зашифрованное хранилище и рефакторинг Storage API в BeSafeChat

## Обзор

BeSafeChat реализует комплексное сквозное шифрование (E2EE) для локально хранящихся сообщений и конфиденциальных данных. Все данные, сохраняемые в IndexedDB, шифруются с использованием пользовательских ключей, что обеспечивает приватность и безопасность даже при компрометации устройства.

В ходе последнего рефакторинга была полностью переработана архитектура управления криптографическими ключами: переход на **неэкспортируемые `CryptoKey`**, явная передача `identityId`, удаление устаревших полей и усиление защиты от XSS-атак.

---

## Алгоритмы шифрования

### Основной алгоритм шифрования

- **AES-GCM (Advanced Encryption Standard — Galois/Counter Mode)** с ключами 256 бит
- Обеспечивает одновременно **конфиденциальность** и **аутентичность** данных
- Использует 12-байтный вектор инициализации (IV) и 16-байтный тег аутентификации (authTag)

### Функция деривации ключей (KDF)

- **PBKDF2 (Password-Based Key Derivation Function 2)** с хэш-функцией SHA-256
- **100 000 итераций** (оптимизировано для high-entropy входных данных)
- Соль формируется как `${handleId}:${purpose}` для обеспечения:
  - Уникальности ключей для каждого пользователя (`handleId`)
  - Разделения ключей по контекстам использования (`purpose`: `'message'`, `'file'`, `'contact'`, `'metadata'`)

## Архитектура StorageService

### Класс `StorageService`

Центральный компонент для управления всеми операциями зашифрованного хранилища. Расположен в `frontend/app/services/storage.service.ts`.

### Ключевые методы

| Метод                         | Назначение                                           |
| ----------------------------- | ---------------------------------------------------- |
| `saveEncryptedMessage()`      | Шифрование и сохранение сообщения в IndexedDB        |
| `loadDecryptedMessages()`     | Загрузка и расшифровка сообщений из IndexedDB        |
| `encryptTextData()`           | Шифрование текстовых данных общего назначения        |
| `encryptBinaryData()`         | Шифрование бинарных данных (файлы, изображения)      |
| `decryptData()`               | Расшифровка данных общего назначения                 |
| `decryptTextData()`           | Расшифровка текстовых данных                         |
| `storeEncryptionKey()`        | Сохранение неэкспортируемого `CryptoKey` в IndexedDB |
| `loadEncryptionKey()`         | Загрузка `CryptoKey` из IndexedDB                    |
| `deleteEncryptionKey()`       | Удаление ключа при выходе из аккаунта                |
| `verifyEncryptionIntegrity()` | Проверка целостности зашифрованных данных            |

## Процесс шифрования

### Поток шифрования сообщения

1. Текстовое содержимое конвертируется в UTF-8 байты (`TextEncoder`)
2. Получается базовый `CryptoKey` (из RAM-кэша или IndexedDB) через `getBaseKey(identityId)`
3. Через `deriveEncryptionKeyFromHash()` деривируется контекстный ключ AES-GCM:
   - Соль: `${handleId}:${purpose}`
   - Iterations: 100 000
   - Hash: SHA-256
4. AES-GCM шифрует контент со случайным IV
5. Результат: `{ encrypted: Uint8Array, iv: Uint8Array, context, timestamp }`
6. Данные сохраняются в IndexedDB в таблице `messages`

### Структура хранимых данных

```typescript
interface EncryptedStorage {
  encrypted: Uint8Array; // Шифротекст (ciphertext)
  iv: Uint8Array; // 12-байтный вектор инициализации
  context: 'message' | 'contact' | 'metadata' | 'file'; // Контекст использования
  timestamp: number; // Время шифрования
  // ❌ version: удалено (теперь только одна версия)
  // ❌ salt: удалено (уникальность обеспечивается через handleId в KDF)
  // ❌ authTag: не хранится отдельно (встроен в AES-GCM)
}
```

### Структура сообщения в IndexedDB (`Message` интерфейс)

```typescript
interface Message {
  id: string;
  chatId: string;
  senderId: string;
  contentType: 'text' | 'image' | 'file';

  // Шифрованные данные
  encryptedContent: ArrayBuffer; // Зашифрованное содержимое
  iv: ArrayBuffer; // Вектор инициализации

  // Метаданные
  timestamp: number;
  isOwn: boolean;

  // Опциональные поля
  status?: 'sending' | 'sent' | 'delivered' | 'read' | 'failed';
  editedAt?: number;
  replyToId?: string;
  metadata?: Record<string, any>;
}
```

## Управление ключами: новая архитектура

### 🔐 Non-extractable CryptoKey

Ключевое изменение: вместо хранения хэша приватного ключа в виде `Uint8Array` в RAM, теперь используется **неэкспортируемый `CryptoKey`**, который:

- ✅ **Нельзя прочитать** через JavaScript (`extractable: false`)
- ✅ **Можно использовать** для криптографических операций (`deriveKey`, `encrypt`, `decrypt`)
- ✅ **Сохраняется в IndexedDB** для восстановления после перезагрузки страницы
- ✅ **Защищён от XSS**: вредоносный скрипт может использовать ключ, но не может его украсть

### Поток работы с ключом

```
[Логин / Восстановление аккаунта]
  ↓
Приватный ключ → hashPrivateKey() → importKey(extractable: false) → CryptoKey
  ↓
Сохранение в IndexedDB: StorageService.storeEncryptionKey(identityId, baseKey)
  ↓
Сохранение ссылки в RAM: setSessionCryptoKey(baseKey) [опционально, для производительности]
  ↓
[Отправка / Получение сообщения]
  ↓
getBaseKey(identityId): RAM → IndexedDB fallback
  ↓
deriveEncryptionKeyFromHash(baseKey, handleId, purpose) → AES-GCM ключ
  ↓
Шифрование / Расшифровка
  ↓
[Перезагрузка страницы]
  ↓
getBaseKey() загружает CryptoKey из IndexedDB → работа продолжается бесшовно
  ↓
[Logout]
  ↓
StorageService.deleteEncryptionKey(identityId) + clearSessionCryptoKey()
```

### Методы управления ключом

```typescript
// Сохранение ключа в IndexedDB
static async storeEncryptionKey(identityId: string, key: CryptoKey): Promise<void>

// Загрузка ключа из IndexedDB
static async loadEncryptionKey(identityId: string): Promise<CryptoKey | null>

// Удаление ключа при logout
static async deleteEncryptionKey(identityId: string): Promise<void>

// Вспомогательный метод: получение ключа (RAM → IndexedDB fallback)
private static async getBaseKey(identityId: string): Promise<CryptoKey>
```

## Интеграция с другими сервисами

### Крипто-библиотека (`@/lib/crypto`)

Предоставляет низкоуровневые функции:

- `hashPrivateKey()` — хэширование приватного ключа (SHA-256)
- `deriveEncryptionKeyFromHash()` — деривация ключа шифрования из `CryptoKey`
- `encryptWithKey()` / `decryptWithKey()` — обёртки над Web Crypto API
- `pkcs8ToRawPrivateKey()` — конвертация форматов ключей

### Работа с базой данных (`@/lib/db`)

- Используется **Dexie.js** как обёртка над IndexedDB
- Схема БД динамически создаётся на основе `identityId`: `BeSafeDB_<hash(identityId)>`
- Все операции с данными проходят через `StorageService` — прямой доступ к IndexedDB из компонентов запрещён

### Контекст аутентификации (`useAuth`)

- `identityId` и `handleId` передаются в `StorageService` **явно** как параметры
- ❌ Больше не используется `localStorage` для получения `identityId` (безопасность)
- ✅ Компоненты, имеющие доступ к контексту, передают данные в сервисы

## Жизненный цикл сообщения

### Отправка сообщения

1. Пользователь вводит текст → нажимает "Отправить"
2. `handleSendMessage` в `index.tsx`:
   - Шифрует сообщение через `StorageService.saveEncryptedMessage(..., identityId)`
   - Отправляет зашифрованный контент через WebSocket
   - Сохраняет локальную копию в IndexedDB
3. Получатель:
   - Получает сообщение через WebSocket
   - `handleMessageReceived` сохраняет зашифрованное сообщение в IndexedDB
   - При открытии чата сообщения расшифровываются и отображаются

### Загрузка сообщений

1. `handleChatSelect` вызывает `StorageService.loadDecryptedMessages(chatId, handleId, identityId)`
2. Для каждого сообщения:
   - Загружается `baseKey` через `getBaseKey(identityId)`
   - Деривируется контекстный ключ
   - Расшифровывается контент
3. Результат: массив расшифрованных сообщений для отображения в UI

### Обработка ошибок расшифровки

- При неудачной расшифровке сообщение отображается как `[❌ Сообщение не удалось расшифровать]`
- Ошибка логируется для отладки
- Пользовательский опыт не прерывается

## Особенности безопасности

### Защита от XSS-атак

| Угроза                              | Мера защиты                                                                |
| ----------------------------------- | -------------------------------------------------------------------------- |
| Кража ключа через `exportKey()`     | `extractable: false` — ключ нельзя экспортировать                          |
| Чтение ключа из памяти              | Ключ управляется браузером, не доступен как `Uint8Array`                   |
| Использование ключа злоумышленником | Возможно только в контексте вкладки; сервер защищает через nonce/challenge |

### Разделение ключей (Key Separation)

```
deriveKey(baseKey, salt='user123:message', ...) → ключ для сообщений
deriveKey(baseKey, salt='user123:file', ...)    → ключ для файлов
```

→ Компрометация одного контекста не влияет на другие.

### Zero-Knowledge архитектура

- ✅ Сервер **никогда** не получает приватный ключ, его хэш или производные ключи шифрования
- ✅ Все криптографические операции выполняются **на клиенте**
- ✅ Даже при компрометации сервера сообщения остаются защищёнными

### Безопасное удаление чувствительных данных

```typescript
function secureClearUint8Array(data: Uint8Array): void {
  // Перезапись случайными данными перед очисткой
  crypto.getRandomValues(data);
}
```

→ Защита от дампов памяти и forensics-атак.

## Производительность

### Оптимизации

| Аспект                                | Решение                                           |
| ------------------------------------- | ------------------------------------------------- |
| Частые чтения ключа                   | RAM-кэш (`sessionCryptoKey`) → IndexedDB fallback |
| Деривация ключа для каждого сообщения | Кэширование производных ключей (опционально)      |
| Массовая загрузка сообщений           | Пакетная обработка с прогрессивной расшифровкой   |
| Хранение в IndexedDB                  | `ArrayBuffer` формат для эффективной сериализации |

### Баланс безопасности и скорости

- PBKDF2: 100 000 итераций (достаточно для high-entropy input, не перегружает CPU)
- AES-GCM: аппаратное ускорение в современных браузерах
- Асинхронные операции: не блокируют UI

## Резервное копирование и восстановление

### Облачный бэкап seed-фразы

- Seed шифруется паролем пользователя через `encryptSeedForCloud()`
- Загружается в облачное хранилище через `CloudBackupService`
- При восстановлении: скачивается → расшифровывается → деривируются ключи

### Локальный бэкап

- Пользователь может скачать зашифрованный файл с seed
- Файл защищён паролем, не содержит приватных ключей в явном виде

### Восстановление доступа на новом устройстве

1. Пользователь вводит пароль или seed-фразу
2. Деривируется приватный ключ → импортируется как `CryptoKey`
3. Ключ сохраняется в IndexedDB нового устройства
4. История сообщений синхронизируется при получении

## Рефакторинг Storage & Profile API

### Удаление `avatarUrl` из базы данных

- Поле `avatarUrl` удалено из таблицы `users`
- Путь к аватару теперь детерминирован: `users/{userId}/avatar.{ext}`
- Нет необходимости в записях в БД при загрузке аватара

### Унифицированные эндпоинты для работы с файлами

```
POST   /s3/upload          # Получение presigned URL для загрузки
GET    /s3/download/:key   # Получение presigned URL для скачивания
DELETE /s3/:key            # Удаление файла
```

### Упрощённые эндпоинты профиля

```
GET    /auth/profile            # Получение профиля (аватар определяется по наличию файла в S3)
PATCH  /profile/display-name    # Обновление отображаемого имени
```

### Структура файлов в S3

```
s3://besafe.backet/
└── users/
    └── {userId}/
        ├── avatar.{png|jpg|webp}           # Аватар профиля
        ├── media/
        │   ├── 1234567890-photo.jpg        # Изображения из чата
        │   ├── 1234567891-video.mp4        # Видео из чата
        │   └── 1234567892-voice.ogg        # Голосовые сообщения
        └── documents/
            └── report.pdf                   # Общие документы
```

### Преимущества изменений

1. **Нет записей в БД для медиа** — файлы само-описываемы через путь
2. **Единый API** — один эндпоинт для всех типов файлов
3. **Масштабируемость** — легко добавить новые типы медиа
4. **RESTful** — стандартные CRUD-операции
5. **Безопасность** — пользователь может удалять только свои файлы
6. **Простота** — не нужны эндпоинты подтверждения

## Будущие улучшения

### Возможные направления развития

1. **HKDF вместо PBKDF2** для деривации ключей (быстрее, чище семантика для high-entropy input)
2. **Key rotation** — периодическая смена ключей шифрования с ре-шифрованием истории
3. **Multi-device sync** — безопасная передача ключей между устройствами через зашифрованный канал
4. **Hardware-backed keys** — использование Secure Enclave / TPM при наличии поддержки
5. **Post-quantum cryptography** — подготовка к переходу на квантово-устойчивые алгоритмы
