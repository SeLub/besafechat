# Identity Lifecycle & Soft Delete Policy

## Общее описание

Реализована политика управления жизненным циклом идентичности (Identity Lifecycle) в BeSafeChat, основанная на механизме **Soft Delete** с автоматической очисткой данных. Система гарантирует сохранность контекста переписки при временной неактивности пользователя и обеспечивает полное удаление данных по истечении установленного срока в соответствии с принципами GDPR.

**Ключевая проблема, которую решает решение:**
Ранее при повторном входе пользователя после длительного отсутствия система создавала новую идентичность (`Identity`), что приводило к потере связи со старыми чатами и сообщениями, хранящимися в IndexedDB. Сообщения существовали, но были «сиротами» без привязки к активному аккаунту.

**Решение:**
Внедрен статус «мягкого удаления» (`deletedAt`). Аккаунт не удаляется физически сразу, а скрывается на 90 дней. В этот период пользователь может восстановить доступ через ввод Seed-фразы, при этом все данные (чаты, контакты, профили) возвращаются в активное состояние мгновенно.

## Архитектура данных

### Иерархия связей

Все основные сущности проекта теперь поддерживают поле `deletedAt`. Удаление родителя (`Identity`) должно корректно обрабатывать всех потомков.

```text
Identity (uuid-1, deletedAt)
  ├─ Handles (ownerIdentityId, deletedAt)
  │    ├─ Profiles (handleId, deletedAt)
  │    ├─ Chats (handleId, deletedAt)
  │    │    └─ Messages (senderHandleId/chatId, deletedAt)
  │    ├─ Contact Requests (from/to Handle, deletedAt)
  │    └─ Team Memberships (memberHandleId, deletedAt)
  ├─ Channels (ownerIdentityId, deletedAt)
  │    └─ Channel Messages (chatId, deletedAt)
  └─ Teams (ownerIdentityId, deletedAt)
       ├─ Team Invites (inviter/invited Handle, deletedAt)
       └─ Child Teams (parentTeamId, deletedAt)

Media (uploaderIdentityId, deletedAt) -> Физические файлы в S3 (Tebi)
```

### Изменения в схеме БД

Во все перечисленные сущности добавлено поле:

```typescript
@DeleteDateColumn({ nullable: true })
deletedAt!: Date | null;
```

**Список обновленных сущностей:**

1.  `Identity`
2.  `Handle`
3.  `Profile`
4.  `Chat`
5.  `Channel`
6.  `ContactRequest`
7.  `Media`
8.  `MessageMetadata`
9.  `Team`
10. `TeamMembership` (косвенно, через каскад от Handle/Team)
11. `TeamInvite` (косвенно, через каскад от Handle/Team)

### Правила каскадного удаления (Foreign Keys)

Для обеспечения целостности данных при физическом удалении настроены следующие правила на уровне PostgreSQL (через TypeORM):

| Родитель (Parent) | Потомок (Child)   | Правило (ON DELETE) | Комментарий                                                           |
| :---------------- | :---------------- | :------------------ | :-------------------------------------------------------------------- |
| `Identity`        | `Channel`         | `CASCADE`           | Удаление юзера удаляет его каналы                                     |
| `Identity`        | `Team`            | `CASCADE`           | Удаление юзера удаляет его команды                                    |
| `Handle`          | `Identity`        | `CASCADE`           | (Техническая связь)                                                   |
| `Team`            | `Handle`          | `CASCADE`           | Удаление команды удаляет её системный хендл                           |
| `Team`            | `Team`            | `SET NULL`          | Дочерняя команда становится корневой при удалении родителя            |
| `Channel`         | `Handle`          | `CASCADE`           | Удаление канала удаляет его хендл                                     |
| `Handle`          | `MessageMetadata` | `CASCADE`           | Удаление автора удаляет его сообщения                                 |
| `Handle`          | `ContactRequest`  | `CASCADE`           | Удаление участника удаляет запросы                                    |
| `Handle`          | `TeamMembership`  | `CASCADE`           | Удаление участника удаляет запись о членстве                          |
| `Handle`          | `TeamInvite`      | `CASCADE`           | Удаление участника удаляет инвайты                                    |
| `Identity`        | `Media`           | `SET NULL`          | **Важно:** Ссылка обнуляется, но запись остается для явной очистки S3 |

## Жизненный цикл идентичности

### Фаза 1: Active (Активный)

- **Статус:** `deletedAt IS NULL`.
- **Поведение:** Пользователь может логиниться, отправлять сообщения, создавать чаты.
- **Поиск:** Стандартные запросы TypeORM (`findOne`, `find`) автоматически исключают записи с `deletedAt`, так как используется декоратор `@DeleteDateColumn`.

### Фаза 2: Soft Deleted (Мягкое удаление)

- **Триггер:** Системный процесс или администратор помечает неактивный аккаунт (например, через 1 год бездействия).
- **Статус:** `deletedAt = [Дата удаления]`.
- **Поведение:**
  - Логин по публичному ключу возвращает ошибку «Не найден» (для стандартного флоу).
  - Данные скрыты из выборок, но физически присутствуют в БД.
  - Сообщения в IndexedDB на клиентах остаются нетронутыми.
- **Длительность:** 90 дней.

### Фаза 3: Recovery (Восстановление)

- **Условие:** Пользователь вводит Seed-фразу в окне входа в течение 90 дней после `deletedAt`.
- **Процесс:**
  1.  Frontend деривирует публичный ключ из Seed.
  2.  Backend ищет идентичность **с учетом удаленных** (`withDeleted: true`).
  3.  Проверяется условие: `(ТекущаяДата - deletedAt) < 90 дней`.
  4.  Запускается транзакция восстановления:
      - `deletedAt` устанавливается в `NULL` для `Identity`.
      - Каскадно восстанавливаются все связанные `Handles`, `Profiles`, `Chats`.
  5.  Пользователь получает доступ ко всем старым чатам и данным.
- **Результат:** Аккаунт полностью возвращается в состояние **Active**.

### Фаза 4: Hard Delete (Физическое удаление)

- **Триггер:** Cron Job (`IdentityCleanupService`), запускаемый ежедневно.
- **Условие:** `deletedAt < (ТекущаяДата - 90 дней)`.
- **Процесс:**
  1.  Поиск всех идентичностей, подлежащих удалению.
  2.  Для каждой идентичности:
      - **Очистка S3:** Поиск всех файлов `Media`, загруженных пользователем. Физическое удаление файлов из хранилища Tebi S3 через `MediaService.deleteFile()`.
      - **Очистка БД:** Удаление записей о медиа, сообщениях, чатах, каналах, командах и хендлах.
      - **Финал:** Физическое удаление записи `Identity`.
- **Результат:** Данные безвозвратно удалены. Восстановление невозможно.

## Техническая реализация (Backend)

### 1. Модификация сервисов

#### `IdentityService`

Добавлены методы для работы с удаленными записями:

- `findByIdentityPublicKey()`: Ищет только активные (стандартное поведение TypeORM).
- `findDeletedByPublicKey()`: Ищет только записи с `deletedAt != NULL` (использует `withDeleted: true`).
- `recoverIdentity(identityId)`: Транзакционный метод, который сбрасывает `deletedAt` в `NULL` для цепочки сущностей: `Identity` → `Handle` → `Profile` → `Chat`.

#### `AuthService`

Обновлен метод `loginWithPublicKey()`:

1.  Попытка найти активный аккаунт.
2.  Если не найден → попытка найти удаленный аккаунт.
3.  Если удаленный найден:
    - Проверка срока (90 дней).
    - Если срок истек → Ошибка `403 Forbidden`.
    - Если срок в норме → Вызов `identityService.recoverIdentity()`.
4.  Возврат токенов и флага `recovered: true` (для уведомления фронтенда).

#### `IdentityCleanupService`

Новый сервис с планировщиком задач (`@nestjs/schedule`).

- **Метод:** `handleHardDelete()` (Cron: каждый день в 03:00).
- **Логика:**
  - Находит «просроченные» идентичности.
  - Запускает `deleteIdentityCascade()` для каждой.
  - **Критический шаг:** Перед удалением записи из БД вызывает `mediaService.deleteFile()` для каждого файла пользователя, чтобы очистить облачное хранилище.
  - Использует транзакции для гарантии целостности БД.

### 2. Конфигурация модулей

- **`AppModule`**: Добавлен импорт `ScheduleModule.forRoot()` для активации Cron-задач.
- **`IdentityModule`**:
  - Зарегистрированы все сущности, участвующие в каскадном удалении (`Channel`, `Team`, `Media` и др.).
  - Импортирован `MediaModule` (через `forwardRef`) для доступа к сервису удаления файлов.
  - Добавлен провайдер `IdentityCleanupService`.

### 3. Тестирование

Реализован набор тестов для верификации политики:

#### Integration Test: `identity-lifecycle.integration.spec.ts`

Проверяет полный цикл на реальной тестовой базе данных:

1.  **Создание:** Генерация полной структуры данных (Identity + Handle + Channel + Team + Media + Message).
2.  **Soft Delete:** Эмуляция установки `deletedAt` в прошлое (10 дней назад). Проверка, что запись скрыта, но существует.
3.  **Recovery:** Восстановление записи и проверка, что `deletedAt` обнулился.
4.  **Hard Delete:**
    - Установка `deletedAt` > 90 дней.
    - Запуск сервиса очистки.
    - **Ассерты:**
      - Все записи (Identity, Handle, Channel, Team, Message) удалены из БД (даже с флагом `withDeleted: true`).
      - Метод `MediaService.deleteFile` был вызван с правильными ключами (проверка через Mock).

## Безопасность и соответствие стандартам

### GDPR Compliance

- **Право на забвение:** Реализовано автоматическое полное удаление данных пользователя по истечении разумного срока хранения (90 дней после деактивации).
- **Прозрачность:** Пользователь уведомляется о возможности восстановления в течение этого периода.

### Целостность данных

- **Транзакционность:** Операции восстановления и удаления выполняются в рамках транзакций БД. При ошибке на любом этапе изменения откатываются.
- **Защита от «мусора» в S3:** Явная логика очистки файлов перед удалением метаданных из БД предотвращает появление бесхозных файлов в облачном хранилище.

### Изоляция данных

- **Soft Delete:** Данные неактивных пользователей изолированы от активных выборок на уровне ORM, что исключает случайную утечку или отображение «мертвых душ» в интерфейсе.

## Сценарии использования

### Сценарий 1: Возвращение пользователя (Успешное восстановление)

1.  Пользователь не заходил в приложение 1 год и 10 дней.
2.  Аккаунт был помечен как `Soft Deleted` (дата удаления = 1 год назад).
3.  Пользователь открывает приложение, вводит Seed-фразу.
4.  Система находит удаленный аккаунт, проверяет дату (10 дней < 90 дней).
5.  Происходит восстановление: все чаты, контакты и настройки становятся активными.
6.  Пользователь видит сообщение: «Аккаунт успешно восстановлен».

### Сценарий 2: Истечение срока восстановления

1.  Пользователь не заходил 1 год и 4 месяца.
2.  Аккаунт был помечен как `Soft Deleted` (дата удаления = 1 год и 3 месяца назад).
3.  Пользователь вводит Seed-фразу.
4.  Система проверяет дату: 91 день > 90 дней.
5.  Возвращается ошибка: «Срок восстановления аккаунта истек. Данные удалены безвозвратно».
6.  Предлагается создать новый аккаунт (старые данные потеряны).

### Сценарий 3: Автоматическая очистка (Cron Job)

1.  Наступает 03:00 ночи.
2.  `IdentityCleanupService` сканирует таблицу `identities`.
3.  Находит аккаунты, у которых `deletedAt` старше 90 дней.
4.  Для каждого аккаунта:
    - Удаляет 50 файлов аватарок и вложений из Tebi S3.
    - Удаляет записи о файлах, сообщениях и профилях из PostgreSQL.
    - Удаляет запись `Identity`.
5.  В логах появляется запись: «Successfully hard deleted X accounts».
