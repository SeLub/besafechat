# Техническое задание: Обновление frontend для работы с identity-based архитектурой

## 1. Обзор изменений в архитектуре

### 1.1. Основные изменения

В системе произошла миграция с пользовательской модели (User-based) на identity-based архитектуру, которая включает следующие ключевые изменения:

1. **Identity** - криптографическая сущность, представляющая уникальную идентичность пользователя (на основе Ed25519 публичного ключа)
2. **Handle** - идентификаторы, используемые для поиска и адресации (username, email, phone и т.д.)
3. **Profile** - персональные данные, связанные с конкретным Handle
4. **Session** - сессии аутентификации, привязанные к Identity и Handle

### 1.2. Важные особенности

- Теперь один Identity может иметь несколько Handle
- Handle могут быть разных типов: 'account', 'team', 'channel'
- Profile связан с Handle, а не напрямую с Identity
- Сессии аутентифицируются через Identity, но работают с определенным Handle

## 2. Изменения в API интерфейсах

### 2.1. Аутентификация

**Старый подход:**

- Авторизация через username/password или просто username
- Пользовательский ID был основным идентификатором

**Новый подход:**

- Авторизация через публичный ключ Ed25519
- Identity ID теперь основной идентификатор пользователя
- Handle используется для адресации и отображения

**Изменения в контроллерах:**

- `/auth/register` - регистрация Identity без Handle
- `/auth/register-with-handle` - полная регистрация с Handle и Profile
- `/auth/login` - вход с использованием публичного ключа
- `/auth/profile` - получение информации о текущем профиле

### 2.2. Управление Handle

**Новые эндпоинты:**

- `GET /handles` - получить все Handle текущего Identity
- `POST /handles` - создать новый Handle
- `PUT /handles/:id` - обновить Handle
- `DELETE /handles/:id` - удалить Handle
- `POST /handles/:id/alias` - установить псевдоним
- `POST /handles/:id/searchable` - установить видимость
- `POST /handles/primary/:id` - установить первичный Handle

### 2.3. Управление профилем

**Изменения:**

- Профили теперь связаны с Handle, а не напрямую с Identity
- `/profiles/me` - получить профиль текущего Handle
- `/profiles/public/:handle` - получить публичный профиль по Handle
- `/profiles/search` - поиск публичных профилей
- `/profiles` (POST/PUT/DELETE) - управление профилем текущего Handle

## 3. Требования к обновлению frontend

### 3.1. Аутентификация и регистрация

#### 3.1.1. Регистрация

1. **Создание Identity:**
   - Генерация пары Ed25519 ключей на клиенте
   - Отправка публичного ключа на сервер через `/auth/register`
   - Получение сессии без Handle

2. **Создание Handle и Profile:**
   - Полная регистрация с Handle через `/auth/register-with-handle`
   - В DTO RegisterWithHandleDto передаются: publicKey, handle, displayName, deviceName, deviceType, userAgent, isSearchable
   - Сервер проверяет доступность handle и создает связанные сущности

3. **Обновление компонентов:**
   - `AuthForm` - должен генерировать ключи и использовать публичный ключ для аутентификации
   - `RegistrationFlow` - реализовать два возможных пути:
     - Быстрая регистрация: сразу создание Identity + Handle через `/auth/register-with-handle`
     - Пошаговая регистрация: сначала `/auth/register`, затем отдельно создание Handle

#### 3.1.2. Вход в систему

1. **Аутентификация:**
   - Сохранение приватного ключа в безопасном месте (IndexedDB с шифрованием)
   - Использование публичного ключа для `/auth/login`
   - Обработка сессии через cookies

2. **Обновление сервисов:**
   - `AuthService` - адаптировать под работу с ключами
   - `UserService` - обновить под новую модель данных

### 3.2. Управление профилем и Handle

#### 3.2.1. Компоненты профиля

1. **Отображение профиля:**
   - Обновить `UserProfile` компонент для отображения информации из новой структуры
   - Поддержка переключения между Handle (через `/auth/switch-handle`)

2. **Редактирование профиля:**
   - `ProfileEditModal` - обновить для работы с новыми полями
   - Добавить возможность управления несколькими Handle

#### 3.2. Управление Handle

2. **Создание чатов:**
